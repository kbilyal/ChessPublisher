1. Installation, start and tournament files

Chess-Publisher is distributed as a portable Windows package. Extract the complete package to a writable folder and start ChessPublisher.exe. Keep the executable, HTML application, WebView/Cloud adapters and engine folder together. Do not move only the EXE out of the package.

The title bar identifies the running version and the current FIDE Mode state. Use Save for an explicit durable save. Autosave can be enabled from the title bar. A tournament should be saved before closing the application, before moving the package, and before external transfer.

Create or open a tournament

  • Create a local Swiss or Round Robin event from the New Tournament dialog.
  • Use the Online option only after an Organizer Token has been connected for the current installation.
  • When reopening an existing tournament, verify the tournament name and round in the title/workspace before entering new data.
Version rule: do not edit the internal package files or replace the bundled pairing/checker engines. Tournament data and exports are the supported working surfaces.

2. Tournament Setup

Tournament Setup contains the event parameters used by pairing, exports and online publishing. Complete the event name, federation/location data, dates, number of rounds, time control, rating type and tournament format before Round 1.

Swiss

Individual Swiss events use the FIDE Dutch workflow through the bundled pairing engine. The announced number of rounds is important for pairing validation, Article-16 tie-break calculations and TRF output. If the round count is changed after pairing has started, FIDE Mode applies the compliance warning/revalidation workflow.

Round Robin

Round Robin uses Berger Tables. Finalize the roster and TPN assignment before schedule generation. The program supports the public-draw TPN workflow and the automatic starting-list route. Once Round 1 has been paired, pairing-identity settings are intentionally restricted.

Baku Acceleration

For eligible Swiss events, choose the Baku Acceleration Method before Round 1. Chess-Publisher passes the acceleration information to the bundled FIDE Dutch engine through TRF26 acceleration records. After Round 1 has ever been paired, the Baku configuration is locked.

Scoring and PAB

Use the tournament scoring settings before pairing starts. Pairing-allocated bye (PAB) points are tournament configuration. A post-start PAB change is treated as a sensitive action and existing pairings are revalidated.

3. Lists & Players, registration and TPN

Use Lists & Players to register competitors from the FIDE database or manually. Verify name, federation, FIDE ID, rating, title, gender/birth data where required, and entry status.

Official Rating and Tournament Rating

Chess-Publisher keeps the Official Rating used for FIDE rating reporting separate from the Tournament Rating used for tournament operations. The Official Rating is used by FIDE Rating TRF16/TRF26 reporting and by registered-player rating consistency checks. The Tournament Rating is used for starting-order calculations, seeding, TPN ranking and pairing operations. Updating an Official Rating from a verified FIDE list does not silently change the Tournament Rating. In Edit Player, the two values are shown separately as Official Rating (FIDE report) and Tournament Rating (operations).

Tournament Rating Method

The Tournament Rating Method controls how the Tournament Rating used to rank players and assign TPNs is derived. Available methods are FIDE, NRO (National Rating), FIDON (FIDE then National), NIDOF (National then FIDE), HBFN (highest available FIDE/National/manual Tournament Rating) and OTHER (the explicitly entered Manual Tournament Rating). Edit Player also retains National Rating and Manual Tournament Rating source fields. Changing a Tournament Rating that affects the starting order uses the normal Resort Starting List safeguards.

When National Rating Support affects ranking, TRF26 exchange includes National Rating Support records and Record 172. If a manual Tournament Rating is what makes an HBFN selection differ from the standard TRF26 FIDE/National maximum, Chess-Publisher exports the ranking method as OTHER so the exchange file does not mislabel the method.

Rating sources

Chess-Publisher keeps provenance for stored ratings. A rating loaded from a FIDE or National source retains the source list and the value obtained from that source. If the arbiter later edits the value manually, the original source is preserved and the current value is marked as manually overridden. A value entered manually from the start is stored as Manual / no source. Imported values whose exact source list is not available are kept as source unavailable rather than being assigned an invented source. The concise source summary is visible in Edit Player.

Rating List Library — Custom and Type-B lists

Rating List Library is a searchable installation-wide library. Importing a national, regional, club or historical list does not register its rows as tournament participants. The imported list can be reused by multiple tournaments.

  1. Open Lists & Players → Rating List Library → Import Rating List….
  2. Select the source file and identify the list name, category and rating type.
  3. After import, search in Search player (FIDE + imported rating lists)….
  4. Add only the selected player. If the same person is present in more than one list, the Add Player rating dialog shows all available rating sources and recommends the source selected by the tournament Rating List Sequence.

Imported lists whose original authority cannot be verified by Chess-Publisher are retained as Type-B lists. They are never silently promoted to Type-A. Each list has a stable internal identity independent of its visible name. Duplicate display names therefore do not merge list identities.

Identity matching: equal valid FIDE IDs are treated as the same player. When no FIDE ID is available, an automatic merge requires an exact Name + Federation + full Date of Birth match. Name-only or Name + Federation matches remain separate so two different players are not accidentally merged.

Provenance: selecting an imported rating stores the source-list identity and source value. A later manual edit keeps that original provenance and marks the Tournament Rating as manually overridden. Deleting a local list does not erase historical player provenance.

Do not use Import Players for a federation rating list. Import Players registers rows as tournament participants. Use Rating List Library for searchable reference lists.

Starting list / TPN

  • Resort Starting List recalculates the starting order using the configured FIDE ordering while preserving player identity and pairing history.
  • TPN Exchange is available in Swiss tournaments before Round 4 is paired. Select two or more players with the same Tournament Rating, choose a permutation of their existing TPNs and confirm the Level-3 warning. If the exchange changes the standard FIDE-title order, the warning states this explicitly.
  • When a rule-based TPN regeneration would change two or more TPNs, FIDE Mode requires Level-3 confirmation and records the regeneration in the compliance log.
  • A genuine late entry can still receive the appropriate TPN after Round 4 through the Late Entry + Resort workflow; historical boards and results are not rewritten.
  • For Round Robin public draws, use Enter TPN Draw. Enter every number from 1 to N exactly once.

Late entry

Add a late entrant through the dedicated late-entry workflow. Previous rounds remain zero/unplayed as applicable and the player becomes eligible from the configured joining round. Do not create a late entrant by manually changing an existing player's identity.

Withdrawal / exclusion

Use the player-status controls instead of deleting historical pairings. In Round Robin final standings, the program applies the configured FIDE treatment for a withdrawn/expelled participant who completed less than 50% of scheduled games while keeping original history for rating/audit purposes.

4. Pairings

Generate pairings

  1. Confirm all required results from the previous round.
  2. Check active/withdrawn/late-entry player status.
  3. Confirm round-specific bye/exclusion settings.
  4. Generate the next round.
  5. Review the pairing list before publishing or entering results.

Chess-Publisher blocks generation when required preceding results are missing. The independent pairing-integrity path is used around imported pairings, Manual Pairing and sensitive configuration changes.

Previous-round correction window

For Swiss tournaments, FIDE C.04.2:4.3 allows a narrow correction window for the round immediately preceding the current paired round. If Round N has already been paired but has not yet ended, the arbiter may reopen Round N−1 through the dedicated correction control after a Level-3 confirmation. A result, colour assignment or permitted Manual Pairing datum can be corrected, but the already published Round N pairing is not rewritten. The corrected history is used for the next pairing still to be made. When Round N ends, the live correction window closes automatically. A later discovery is handled through the separate post-tournament Rating Report Corrections workflow and does not rewrite event standings/history.

Manual Pairing

Use Manual Pairing only when an arbiter intentionally needs to alter a generated pairing. Existing populated boards cannot be silently deleted. The program checks absolute criteria and, when leaving Manual Pairing after a structural change, compares the prepared pairing with the correct pairing. In a Round Robin tournament, finalisation also checks the complete schedule: every player must meet every other player exactly once per cycle, with valid free-day rows for odd fields. An incomplete or inconsistent Round Robin schedule keeps Manual Pairing open. In FIDE Mode, a pairing discrepancy uses the configured warning and PIBE audit workflow.

Prohibited pairings

Pre-defined prohibited player pairs can be configured before Round 1 and may apply to all or selected rounds. After Round 1 has ever been paired, this configuration is locked. Generated and manually edited pairings are checked before commit.

Board order vs pairing identity

Changing presentation board order is not the same as changing opponents or colours. Pairing-integrity checks compare the actual opponent/colour structure and do not flag a presentation-only board reorder as a different pairing.

Published pairing board order

Before a Pairings PDF/TXT or Program Pairings Telegram publication, Chess-Publisher verifies the FIDE publication order without silently renumbering the authoritative pairing. Ordinary pairs must be ordered by the score of the higher-ranked participant, then by the combined score of both players, then by the lower TPN of the higher-ranked participant. With Baku acceleration, the ordering score uses the player's actual points plus the applicable virtual points. If the stored board order does not satisfy the rule, publication is blocked so the arbiter can correct the authoritative pairing/order explicitly.

Select a real board and use the result palette. A forfeit or unusual OTB result requires two paired players. A BYE requires the appropriate single-player board. Invalid mixed/inconsistent scores are not accepted by the normal result palette.

Swap Colors

Swap Colors exchanges White/Black on the selected real pairing and transforms asymmetric results consistently. Use it only where the pairing structure itself is intended to change.

Adjourned

Mark a real paired game as Adjourned only while it has no final result. It remains unresolved and therefore does not become a provisional tournament score. In FIDE Mode, marking the game Adjourned is a PIBE and requires a cancelable Level-3 warning before the change is committed. The event is logged at Level 3 for the compliance/TRF audit trail. A final result can be entered later, including from the historical round workflow; resolving an adjourned game with a non-draw result also invokes the Level-3 warning/audit path.

The program does not generate a new pairing while an unresolved required result exists. Final standings/final FIDE TRF are likewise not completed while an Adjourned game remains unresolved.

6. Standings and tie-breaks

Standings are derived from the stored pairing/result history. Tournament points are always the primary ordering criterion, followed by the selected tie-break priority.

Swiss mandatory catalogue

The Swiss catalogue includes the mandatory FIDE families supported by this version, including AOB/AOB-F, performance/rating criteria, ARO Cut/Median variants, Buchholz variants, BPG/BWG, DE/DE-P, Fore Buchholz variants, Progressive Score variants, REP, RTNG, Sonneborn-Berger variants, STD, TPN and WIN/WON.

Round Robin mandatory catalogue

Round Robin exposes the applicable mandatory criteria including DE, BPG, BWG, REP, STD, SB and cuts, RTNG, TPN and Koya limit variants. Swiss-only Buchholz/AOB criteria are not offered for Round Robin.

Changing tie-breaks after start

Changing the tie-break list or parameters after pairing has started is a sensitive FIDE Mode action. The program issues the configured high-level warning and, if accepted, records the round and previous/new list in the compliance audit/TRF comment stream.

7. TRF16, TRF26 and ITDX

FIDE Rating TRF26

Use the FIDE Rating TRF26 export for the current exchange/reporting workflow. Before submission, run TRF26 Check. Chess-Publisher validates fixed-width structure, tournament metadata, round history and tie-break exchange data and can use the bundled checker path where available.

TRF26 record 212 carries the ranking/tie-break descriptors. Baku acceleration and prohibited-pairing exchange use their dedicated records. Unusual OTB scores are preserved using a reciprocal played-game record plus the official abnormal-points adjustment record where required.

Final TRF completeness. The final FIDE Rating TRF26 consolidates all tournament events already modeled by Chess-Publisher into the active reporting path. This includes Baku acceleration Record 250, unusual-result Record 299, the current Record 212, post-tournament rating-report corrections and applicable PIBE/compliance/Adjourned ### audit comments. Duplicate audit records are suppressed and round-scoped records are limited to the exported round range. ITDX and non-rating exports keep their separate semantics.

TRF16

TRF16 is retained as a legacy/compatibility export. Do not substitute it for TRF26 where the receiving authority requires TRF26.

ITDX

Use ITDX TRF26 when unresolved Adjourned games must be represented as unknown. Chess-Publisher writes ? in the unresolved result slot and can import this representation back as Adjourned.

Import Results

Imported TRF26 pairing history is checked before durable commit. Pairing discrepancies are surfaced through the FIDE compliance workflow instead of being silently accepted.

Download Results from Web

In Pairings, use ↓ Download Results to retrieve result values entered in the linked Web/Cloud tournament without replacing pairings, players or tournament settings. The download matches existing boards by round and player identity. A blank Web result never clears an existing Desktop result. If Web and Desktop contain different non-blank results for the same board, Chess-Publisher asks before replacing the Desktop result. Any pairing/player mismatch stops the operation fail-closed and directs the arbiter to the full Cloud Pull/Conflict workflow.

8. FIDE Mode, warnings and audit trail

New tournaments start in FIDE MODE. The title bar permanently shows the current mode. Exiting FIDE Mode is an explicit, protected action; after a tournament exits, it cannot silently re-enter FIDE Mode.

LevelOperational meaning in Chess-Publisher
1–2Informational / confirmation warnings for lower-risk exceptional actions.
3Significant compliance warning; cancellation blocks the action where the workflow is fail-closed.
4High-risk action requiring the stronger confirmation flow.
5Prohibited in FIDE Mode; the action is blocked.

PIBE / compliance events

Pairing-integrity-breaching or other sensitive actions are recorded by the common compliance event model. Every current user-finalised PIBE is protected by a cancelable warning of at least Level 3; automatically detected prohibited pairing conflicts are blocked at Level 5. Applicable PIBE events are serialized into TRF comments (###) by the active FIDE Rating TRF path, with duplicate audit records suppressed.

Exact tied final places

When all announced final-standing criteria remain exactly equal, Chess-Publisher can keep the players on the same final place instead of silently applying an unannounced fallback. Same-place mode uses competition ranking (for example 1, 1, 3). The final-place control also offers an explicit Drawing of lots simulation and Manual order tied players. Repeating a lot creates a new persisted draw and audit record. These controls change only the final ordering/rank inside the exact tied group; they do not change scores, tie-break calculations, pairing history or the protected tie-break core. Onscreen, Telegram/plain-text and TXT/print final standings use the same final-rank semantics.

9. Online Hub and Cloud continuation

The Online & Cloud workflow is designed to keep a tournament's stable identity while moving between desktop and supported web workflows. Use the Organizer Token configured for the current installation. Do not share or embed the token in tournament files.

  • Publish Online pushes the current saved tournament snapshot to the online workflow.
  • Pull Changes brings a newer remote state back through the conflict/continuity path.
  • ↓ Download Results in Pairings is a narrow results-only read from Web/Cloud; it never downloads a different pairing or tournament setup.
  • Before publishing, Chess-Publisher saves the current tournament state so recent Setup/Schedule/Regulations changes are included.
When desktop and web have both changed the same tournament, inspect the conflict information before accepting a replacement snapshot. Do not overwrite a known newer tournament state blindly.

10. Chess-Results

The Chess-Results workflow uses the organizer's authenticated token and the protected backend/bridge integration. Use the Chess-Results tab or the relevant Publish action to create/publish/update the current tournament. Ownership and TNR mapping are checked by the integration.

Before publishing, verify tournament type, federation, TNR, round, starting list/pairings/results and that the current tournament is the one intended for the organizer account. Use unlink/delete-authorize actions only when intentionally changing the association.

11. DGT Boards

Use DGT Boards to map tournament boards and manage the supported PGN/live-board workflow. Configure board mapping before live use and verify that the intended tournament/round is open. Keep PGN storage within the tournament's configured output path. DGT operation does not replace the authoritative result entry and tournament history in Chess-Publisher.

12. Tournament Schedule, regulations and exports

Tournament Schedule stores round/event times used by the application and relevant exports. Maintain correct dates before final TRF export. Additional regulations can be stored with the tournament and published through the supported Online Hub workflow.

Other / Export contains additional print/export functions. Use the exact export needed by the receiving system; do not edit fixed-width TRF files in a word processor.

13. Save, backup and recovery

  • Use explicit Save before external publishing/import/export and before closing.
  • Autosave protects routine edits but does not replace release/back-up discipline.
  • Automatic TRF recovery payloads preserve cumulative generated-round information for emergency recovery.
  • When restoring/importing, review the current round and standings before continuing pairings.
  • Do not manually merge two tournament files by copying JSON fragments.

14. Recommended FIDE tournament workflow

  1. Create the tournament; keep FIDE Mode active.
  2. Complete Setup, dates, rounds, time control, format, scoring/PAB, acceleration and tie-break list.
  3. Register/verify players; finalize starting list/TPN.
  4. Configure prohibited pairings and pre-R1 restrictions where needed.
  5. Generate Round 1 and review pairings.
  6. Publish/print pairings as required.
  7. Enter results; resolve missing/Adjourned games before the next pairing.
  8. Generate each next round only after the completion gate passes.
  9. Review standings and any warnings/PIBE actions during the event.
  10. At event end, confirm all results, final standings and tie-break priority.
  11. Run TRF26 Check and export the final FIDE Rating TRF26.
  12. Keep the tournament package/data and submitted TRF as the event archive.

15. Troubleshooting and verification

Gacrux engine runtime reliability

Chess-Publisher keeps the bundled Gacrux 1.9.57 files immutable, but on Windows it does not execute the PyInstaller engine from a deeply nested portable-package path. At Desktop startup, the launcher verifies a manifest-pinned engine runtime and prepares a short per-user runtime path under Local AppData (or the per-user TEMP directory when necessary). Critical loader files, including python314.dll, the Visual C++ runtime and the executable, are checked by SHA256 before use. If the runtime is missing, incomplete, corrupted or fails the executable boot preflight, Chess-Publisher performs one automatic rebuild from the sealed SHA256-pinned engine/g1957.zip archive and verifies the complete 61-file tree before retrying. No administrator registry change, symlink/junction or manual engine copy is required. If the verified runtime still cannot start, the operation stops with a diagnostic instead of silently using an unverified engine.

Engine integrity: the upstream Gacrux 1.9.57 tree in the package remains byte-for-byte unchanged. The short runtime is a verified execution copy used only to avoid Windows loader/path failures and damaged external extraction.

16. Detailed operational checks

Before Round 1

Perform a final pre-pairing review. Confirm the announced number of rounds, tournament format, scoring/PAB value, acceleration choice, selected tie-break priority, tournament dates, time control and rating type. Review the complete player list for duplicate identities, incorrect FIDE IDs, wrong ratings and accidental withdrawn/deleted status. For Swiss events, establish any prohibited pairings before the first pairing is generated. For Round Robin, confirm the final TPN assignment and Berger schedule source. Once Round 1 has been paired, several identity and configuration settings intentionally become restricted.

Before each next round

Use the Pairings workspace as the operational checkpoint. Verify that the displayed selected round is the round being worked on. Resolve every required game result from the previous round, including any Adjourned game that must be decided before pairing can continue. Confirm late entries and withdrawals before generation. If a warning or pairing-integrity comparison appears, read the discrepancy before accepting any override. After generation, check board count, all active-player coverage, the pairing-allocated bye when the number of players is odd, colours and any prohibited-pair restriction before publication.

After result entry

Result entry updates the authoritative tournament history. Standard results, forfeits, unusual OTB awards and byes have different semantics, so use the matching control rather than entering an approximate score. When a result is corrected within an allowed workflow, recheck standings and the next pairing status. If a board has been marked Adjourned, do not treat a provisional expectation as the final score. The final result should be entered through the Adjourned resolution workflow.

Before final publication

Verify that no required result is missing and no Adjourned game remains unresolved. Review the final tie-break priority against the event regulations. If the tie-break list was changed after the event started, confirm that the compliance event is present. Run the TRF26 checker and correct any exchange-structure, date, ranking-descriptor or history error. Preserve the final exported TRF together with the tournament data used to create it.

FIDE database updates and player data

The FIDE database assists registration but does not remove the arbiter's responsibility to use the correct player identity. When updating or searching the database, verify FIDE ID first when possible, then name, federation, title and rating. Do not replace one registered player's identity with another player's data after that identity has already participated in pairings.

Maintained official-list freshness. While Chess-Publisher is running, the maintained official Standard, Rapid and Blitz lists are automatically reverified before the one-day freshness limit. The application begins a proactive check at 23 hours and rechecks after focus or page resume so system sleep or browser suspension cannot silently carry the maintained lists beyond the verification window. If the server cannot be verified and the window is exceeded, the cached lists remain available for continuity, but their freshness is shown as unverified and freshness-dependent consistency checks stay blocked until verification succeeds.

Date-effective consistency checks. Update Registered Players uses the FIDE monthly rating list valid on the tournament Start Date for events lasting up to 30 days. For events lasting more than 30 days, it uses the list valid on the date of the check. The dialog shows the selected month. Before a user-requested rating consistency check, Chess-Publisher verifies the required list: the current-month path refreshes/checks the maintained FIDE lists against the server, while a historical month requires the exact official archive snapshot. If verification fails, the check stops instead of using an unverified or different list. Player identity metadata can still come from the current FIDE directory; the rating comparison itself uses the selected effective monthly list.

Automatic first-opportunity consistency. After an actual maintained FIDE rating-list content update, Chess-Publisher queues a rating-only consistency comparison. It runs when a tournament with valid FIDE IDs is open and no conflicting FIDE operation is active. The required date-effective list is verified first. The automatic check is a preview only: it does not alter player data. If rating differences are found, the affected players and values are written to a dedicated TXT report. A successful manual Start test or registered-player update can satisfy the same pending list revision, and timestamp-only server reverification does not create duplicate checks.

Official-vs-Tournament rating separation. Registered-player consistency compares the verified FIDE value with the player's Official Rating. Applying a registered-player rating update changes the Official Rating only; the Tournament Rating used for starting order and pairing remains unchanged unless the arbiter explicitly changes the tournament value. Legacy sourced players are migrated from retained FIDE provenance where available so a prior tournament override is not mistaken for the official reporting value.

Effective Rapid and Effective Blitz. Chess-Publisher manages Effective Rapid and Effective Blitz views. If a player has no Rapid rating, Effective Rapid uses the player's Standard rating; if a player has no Blitz rating, Effective Blitz uses the Standard rating. A native Rapid or Blitz rating always takes priority when present. The maintained raw Standard, Rapid and Blitz lists are not overwritten by this fallback. The effective view retains the requested list, the actual source list and the fallback state. Date-effective checks use the Standard list from the same required rating period, including historical months.

Type-A official rating lists. FIDE Standard, FIDE Rapid and FIDE Blitz are managed as Type-A Rating Lists because their original source is known to Chess-Publisher. The list descriptor retains the FIDE Rating Server as the original authority, the applicable rating period and the transport/cache details separately. Exact historical FIDE monthly lists used by date-effective checks keep their official archive source. When an Official Rating is assigned from one of these lists, the player rating provenance retains the Type-A list identity, period and original FIDE source. Imported or otherwise unknown-source lists are not silently promoted to Type-A.

Rating List Sequence. New Standard tournaments use FIDE Standard → FIDE Rapid → FIDE Blitz. New Rapid tournaments use Effective Rapid → FIDE Blitz, and new Blitz tournaments use Effective Blitz → FIDE Rapid. The default sequence follows the tournament rating type until the sequence is explicitly customized; a custom sequence is preserved.

Rating List Sequence consistency. Use Check consistency in the Rating List Sequence control to compare each player's Tournament Rating with the rating that the active ordered sequence would assign. The check uses the date-effective FIDE monthly period, verifies every official list required by the sequence first, applies Effective Rapid/Blitz Standard fallback within that same period, and reports the source list used for each difference. This is a preview-only check and does not change player data. Official Rating consistency for FIDE reporting remains a separate workflow.

Manage Rating List Sequence. In Tournament Setup → Rating List Sequence, choose Manage… to edit the active order. Use Add to include an available list, Remove to exclude a list, and the Up/Down controls to change priority. Ratings are resolved from the top of the sequence downward. Use Default restores the canonical sequence for the current Rating Type. A saved custom sequence remains persistent and is not replaced by later Rating Type changes. Rated tournaments must keep at least one rating list in the sequence.

Long-event rating history

For a tournament lasting more than 30 calendar days, or whenever multiple official ratings may apply during the event, enable Tournament lasts more than 30 days / multiple ratings may apply in Tournament Setup. Chess-Publisher also detects the inclusive start-to-end date span and suggests enabling the long-event workflow when the event exceeds 30 days.

In Edit Player → Manage Long-Event Ratings, add each official rating period and the first/last round for which it applies. Round ranges must not overlap and cannot extend beyond the configured tournament rounds. The stored history does not overwrite the player’s normal Official Rating or Tournament Rating.

C.07:10 rating policy: when a long event uses rating/performance-based tie-breaks, Chess-Publisher warns that such tie-breaks are not recommended where a player may have more than one rating during the tournament. For these rating-based criteria, beta.73 uses FIDE default — First rating unless the tournament regulations explicitly choose another supported policy. Rating valid for each round resolves the official rating applicable to each played encounter round. Explicit rating selection per player requires a valid stored period for every multi-rating player and blocks calculation when a required choice is missing or stale.

Post-tournament rating-report corrections. After the tournament has finished, use Rating Report Corrections when a pairing, colour assignment, or game result is discovered too late to change the event standings. The correction is stored separately and is applied only to FIDE Rating TRF16/TRF26 exports. Pairing history and standings remain exactly as used during the event. The rating report includes a ### comment identifying the corrected submission data and the original event data.

Printing and publication

Pairing and standings exports are presentation outputs derived from the tournament state. Select the intended round and format before printing or publishing. A printed list is not an editable source of tournament history. Corrections must be made in the authoritative tournament workflow and then re-exported. Online Hub and Chess-Results publication should always follow a successful local save so the published state corresponds to the tournament state currently visible to the arbiter.

Manual Pairing audit discipline

Manual Pairing is an exceptional control, not a normal alternative pairing engine. Use it only for an intentional arbiter decision. The program checks opponent identities, colours and other configured integrity conditions and compares the final manual structure against the independent verifier where available. If an override is accepted in FIDE Mode, preserve the resulting compliance/PIBE record. Never alter the underlying TRF, JSON or engine output by hand to avoid a warning.

Data exchange discipline

TRF and ITDX are structured exchange formats. Preserve character positions and line structure by using Chess-Publisher export/import functions. Do not open and resave a fixed-width TRF in software that may change encoding, whitespace or line endings. When importing an exchange file, treat any reported player, round, opponent or result mismatch as a data-integrity issue that must be understood before continuing the tournament.

17. Scope and rule authority

Chess-Publisher implements safeguards intended for FIDE tournament handling, but the arbiter remains responsible for event regulations, correct input and the final submitted report. When this manual and an official regulation conflict, use the current official FIDE regulation and record/resolve the software compliance issue before proceeding.

Half-point bye eligibility

Use Edit Player to mark whether a player is eligible to receive an administrative half-point bye. A player marked ineligible cannot be assigned a ½ BYE. Assigning a second or subsequent ½ BYE requires a Level-3 confirmation in FIDE Mode. If eligibility is removed, future scheduled half-point byes are cleared; historical rounds are not changed.

Assigning a 1 BYE after tournament setup displays a FIDE Level-2 information warning. Confirmed full-point bye assignments are recorded in the tournament compliance log and are included as ### comments in the post-tournament TRF audit trail.

Integrated Rating Lists (Windows beta.72)

FIDE Standard, Rapid and Blitz are installation-local reference data. They are maintained as one logical FIDE-ID keyed generation and are not saved as tournament state.

Update Rating Lists downloads/stages the requested source files, validates them, parses all three lists into a temporary index, performs integrity checks and activates the new generation only after complete success. If any list fails, the report shows ROLLED BACK and the previous complete active database remains available.

Exact numeric FIDE ID lookup is direct. Name search ignores case, accents/diacritics, punctuation and repeated whitespace and uses deterministic token-prefix matching; it does not make fuzzy identity guesses.

Tournament safety: updating the local Rating Lists never changes registered tournament players. When a player is added, the current values are copied into the tournament player record. Use Review Player Updates to compare later list generations. Nothing is applied until explicitly confirmed, and review/update does not automatically resort the starting list or change starting numbers.

My Cloud Tournaments (Windows beta.75)

The Cloud section now uses one user-facing workspace: My Cloud Tournaments. Use ↑ Upload Current to add or update the open Desktop tournament, ↓ Pull Current to bring Cloud changes into that same tournament, Refresh Cloud List to reload the organizer-owned list, and Open to open another Cloud tournament.

Chess-Publisher validates the saved Cloud provider ID against the authenticated organizer workspace before upload. A missing or deleted remote tournament is treated as stale linkage, not as a synchronization conflict: obsolete revision/fingerprint metadata is cleared while the stable internal tournament identity and all tournament content are preserved. If one Cloud row matches the stable internalId, the link is repaired automatically; multiple matches fail closed instead of guessing.

A true two-sided content conflict still never overwrites either copy silently. Pull remains Cloud → Desktop and Upload remains Desktop → Cloud. Local Autosave does not transfer Cloud data. Installation-local credentials, paths and DGT hardware mappings are not replaced by Pull.

Historical-rating tie-break policy (Windows beta.73)

For C.07 Article-10 rating-based tie-breaks, open Tie-Break Settings and choose the rating policy required by the event regulations. FIDE default — First rating is the default. Rating valid for each round applies the stored official rating period that covers each encounter round. Explicit rating selection per player lets the arbiter choose one valid stored rating period for every multi-rating player.

Missing or stale explicit selections are rejected before calculation. Changing this policy does not change Official Rating, Tournament Rating, starting numbers, pairing identities, historical pairings or TRF state. The selected policy is tournament-rule state and travels with the portable tournament object.
